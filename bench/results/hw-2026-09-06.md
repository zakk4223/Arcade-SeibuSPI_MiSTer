# The hardware column, and the 25 MHz gate confirmed

MiSTer at 192.168.1.125, core `b8f07077` (`BUILD_DATE 260906`, the 55/63 clk_cpu
gate, PLAN.md 16.10), `Raiden Fighters Jet (386 Benchmark).mra`, W=8, all 37
tests, run to COMPLETE in one pass. Screens in `hw-2026-09-06-screen.png` (raw,
sideways -- the framebuffer is pre-rotation) and `hw-2026-09-06-table.png`
(rotated CCW and 3x, readable).

Transcribed from the screen rather than captured as `BENCH` lines: the MiSTer's
only output is the text layer, and the table prints ITERS (the HI count) and CYC
but not LO, so `analyze.py` cannot be re-run from it. The numbers below are what
the on-screen table shows.

## What the run proves

The benchmark ROM computes its CYC column from `CPU_CLOCKS_PER_FRAME equ 463072`
(`spi.inc:63`) -- **the real board's 25 MHz constant, hardcoded**. So the ROM has
always been asking "what would these clocks be if the CPU ran at 25 MHz", and
before the gate the answer was wrong by exactly the clock error. That makes the
run a direct measurement of the gate in two independent ways.

### 1. Work per frame dropped by exactly 55/63

The pre-gate reference is `core-2026-09-03.txt`, the same core in Verilator at
28.636364 MHz, W=2. Scaling its HI counts by 8/2 for the window gives what this
run would have printed had the gate done nothing:

| test | ref HI (W=2) | x4, if no gate | measured | ratio |
|---|---|---|---|---|
| NULL | 212098 | 848392 | 740624 | 0.87297 |
| ADD R,R | 9142 | 36568 | 31924 | 0.87300 |
| MOV R,IMM | 6238 | 24952 | 21783 | 0.87300 |
| LOAD | 4713 | 18852 | 16458 | 0.87301 |
| STORE | 4777 | 19108 | 16681 | 0.87299 |
| LOAD MISAL | 1197 | 4788 | 4180 | 0.87302 |
| JCC NOTTKN | 6712 | 26848 | 23437 | 0.87295 |
| ... | | | | |
| FETCH 40K | 29 | 116 | 101 | 0.87069 |

All 37 rows:

    mean ratio                        0.872873   (stdev 0.000495)
    pooled, weighted by iterations    0.872971
    ten largest-N rows                0.872961   (stdev 0.000050)
    predicted 55/63                   0.873016
    error on the pooled figure       -0.0052 %
    "the gate did nothing" would be   1.000000

    implied clk_cpu = 28.636364 x 0.872971 = 24.99870 MHz

The scatter is quantization and nothing else: it tracks 1/N exactly. FETCH 40K
runs 101 iterations and is the worst row at 0.87069; LOOP X2 runs 1,628 and is
next at 0.87152; every row above ten thousand iterations lands on 0.87300 +-
0.00002. The residual -0.005 % on the pooled figure is smaller than the frame
period's own uncertainty and is not worth chasing.

### 2. The CYC column now agrees with the Verilator run at its own clock

Clocks per instruction is a property of the microarchitecture and is invariant to
clock rate -- halve the clock and the iterations per frame halve with it. So the
hardware analysed at 25 MHz must reproduce Verilator analysed at 28.636364 MHz,
and it does:

figure would read 0.873x these -- GAME MIX 3.17 instead of 3.62, CHASE 32K 9.62
instead of 11.02, ADD R,R 0.88 instead of 1.01.

## The one row that is not the same, and it is not the clock

**ROM ADD: 1.01 in Verilator, 0.98 on hardware.** It is the only test that runs
in place out of cartridge ROM instead of being copied to RAM, and it is the only
row that moved by more than quantization. That is the SDRAM path -- the Verilator
model against the real chip through the arbiter -- not the gate, which cannot
produce a per-test difference. Both figures are ~1.0, so the I-cache is absorbing
the fetch latency in both cases and the residual is small; it is recorded here
because it is the only place hardware and simulation disagree, and the real
cartridge run still owes an answer on ROM wait states.

## What this does NOT say

GAME MIX is 3.62 clocks against MAME's 7.38 for a real 386. The clock is now
right and the per-clock margin is untouched: **2.03x**, measured on hardware, all
of it microarchitecture. See PLAN.md 16.10.
